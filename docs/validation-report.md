這份報告不把離線自測當成音訊裝置、驅動或遊戲驗證；所有驗證都沒有安裝驅動、切換預設裝置、向實體裝置播放測試音或建立啟動項。A4 量測仍保留待測。

## 1.0.1 補做（2026-10-04）

1.0.0（`a3cd408`）之後補了三件事：參數變更不再咔嗒、輸出裝置被獨佔時回報並自動恢復、來源封存只收原始碼與建置檔。主會話另外追加三件：新增 `ready` 狀態、`bypass` 不持久化、非 KnownDLL 改延遲載入並限制 DLL 搜尋路徑。1.0.0 後來已由會話 B 公開並以 1U 憑證簽章；1.0.1 是新版本號，不改寫 `v1.0.0`。

### 切換參數的瞬態

自測 `transition` 在串流中途切換參數，量輸出與「兩個穩態結果按同一條淡化曲線混合」的理想值之差。兩個穩態結果是同一段輸入分別一直套用舊參數、一直套用新參數的輸出。輸入為 48 kHz 雙聲道，正弦峰值 0.05（線性滿刻度），白噪音均勻分布於 ±0.05。切換點在第 1 秒，區塊 441 frames，所以淡化會在區塊中間開始與結束。

- 自有段（preamp／EQ／高音）在淡化處直接比對，門檻 ≤1e-6。
- 完整鏈（含上游效果與限幅器）的效果全 0、電平低於限幅，所以上游等於固定增益加 36 frames 預讀延遲；理想值的淡化曲線同樣後移 36 frames，門檻 ≤1e-5（float 捨入等級）。
- 同一度量套在舊做法（換上冷啟動的新濾波器、不淡化）上，結果必須大於自有段門檻的 1000 倍，證明這個度量看得見咔嗒聲。

其他情境：

- 折返：淡化進行到三分之一時改回原參數；排隊：淡化中來第三組參數；替換：排隊中的參數又被更新的取代。三者的自有段誤差都是 0。
- 實際執行緒：另開一條執行緒以 480 frames 區塊持續處理，主執行緒在它運作時套用 8 次參數。依記錄的起點 frame 重算理想值，各次建置的最大誤差在 7.45e-9 到 1.12e-8 之間（float 捨入）；每次第一次持鎖檢查時新濾波器都已追上，重試 0 次。
- 鎖外追趕：新濾波器預熱完之後，串流又前進 1000 frames 才安裝。它從歷史追上後，自有段誤差仍是 0；落後超出歷史容量時則正確回報追不上，由 apply 改為重建再預熱。追趕一律在音訊鎖外進行。
- 44.1 kHz 雙聲道（淡化 882 frames）與 48 kHz 8 聲道：自有段誤差 0。
- 只記錄、不設門檻：20 Hz、Q 10、+20 dB 的共振響鈴比 1.37 秒的歷史還長，預熱只能近似。切到 +14 dB 時殘差 3.74e-5，峰值 0.0551（約 −63 dB）。

保真度重跑結果與 1.0.0 完全相同：13 個內置預設最大 0.105548 dB（逐個數字不變）、效果全 0 平直 8.51406e-7 dB、參數 EQ 14,336 點 ≤0.1 dB。

### 持鎖時間與淡化長度

淡化 20 ms（48 kHz 960 frames、44.1 kHz 882 frames），曲線 sin²。理由：10 ms 對 50 Hz 只有半個週期，大幅度低頻 EQ 變化在這麼短的窗內仍可能聽成一聲「嗒」；超過 30 ms，放開滑桿後的變化會開始顯得拖，圖形與參數互切時兩路延遲差（5.3 ms）造成的短暫梳狀也拉得更長。兩路信號高度相關，所以用等增益曲線，不用等功率曲線（後者會在中段鼓起約 3 dB）。

| apply 種類 | 最長持鎖 | 鎖內做什麼 |
| --- | --- | --- |
| 只改 EQ（自測全部 EQ 切換與實際執行緒情境） | 0.3 µs（3,619 個執行緒週期） | 指標交換、旗標 |
| 改一個效果 | 107 µs | 該效果的上游 setter（會寫登錄檔） |
| 五個效果全改 | 531 µs | 五個上游 setter |

濾波器設計與預熱都在鎖外；自測要求只改 EQ 的 apply 持鎖不超過 2,000,000 個執行緒週期（以執行緒週期計，排除被搶占的時間）。上游 DSP 不是執行緒安全的，所以 setter 仍在鎖內，只呼叫值有變的那幾個。執行期 `status.stats.applyLockMaxUs` 回報同一個數字。

### 獨佔回報與恢復

- 分類：`AUDCLNT_E_DEVICE_IN_USE` → `OUTPUT_EXCLUSIVE_LOCKED`；`S_OK`、`S_FALSE` 視為成功；`AUDCLNT_E_UNSUPPORTED_FORMAT`、`AUDCLNT_E_DEVICE_INVALIDATED`、`AUDCLNT_E_SERVICE_NOT_RUNNING`、`E_FAIL`、`E_OUTOFMEMORY` → `INTERNAL`。HRESULT 格式為 `0x8889000A`、`0x80004005` 這種八位大寫十六進位。
- 測試縫：自測直接呼叫上游所用的掛勾入口 `hikariOnPlaybackInitializeResult` 注入 `AUDCLNT_E_DEVICE_IN_USE`。核對：state 對應為 `idle-no-device`；`lastError` 的 code、message、`hresult`、`device` 與 `ok:false` 逐字吻合；早於基準點的回報會被忽略。
- 重試：模擬 60 秒獨佔，探測剛好 30 次、間隔都是 2000 ms，期間沒有一次讓上游重新初始化；上游沒停住時不做任何事。探到可用時只觸發一次重新初始化，之後成功回報清掉錯誤，state 回到 starting／processing。
- 其他失敗：退避間隔 2、4、8、16、30、30 秒；類別改變時重新起算，同類別換 HRESULT 不重新起算。上游停住但沒有任何回報時，同樣退避，而且不產生 lastError。
- 補丁驗證：`tools/verify-upstream.mjs` 釘住掛勾只出現一次，位置在播放端最後一次 `Initialize` 與 `CoTaskMemFree(pClosestMatch)` 之後、標記裝置不可用的失敗分支之前。`tools/verify-upstream.mutations.mjs` 共 42 個變異全部被拒（原 33 個加新掛勾 9 個），還原後通過。

### 就緒狀態、旁路不持久化、DLL 載入

這三件是主會話核查會話 B 之後追加的，一起放進 1.0.1：

- `ready`：自測窮舉就緒條件的 16 種組合（輸出已初始化、上游沒停住、虛擬裝置是預設或指定不切預設），剛好 3 種成立。狀態對應依序是：輸出失敗 > `bypassed` > `processing` > `ready` > `starting`。
- 旁路不持久化：`bypass:true` 的參數寫成狀態檔時變成 `false`、其餘欄位逐字不變；1.0.0 風格、帶 `bypass:true` 的狀態檔讀回時也是 `false`。
- DLL 載入：建置時的匯入表檢查結果，靜態匯入為 advapi32、kernel32、ole32、shell32、user32，五個都在本機 KnownDLLs 清單內；延遲載入為 cfgmgr32、wtsapi32；KERNEL32 匯入表裡有 `SetDefaultDllDirectories`，原始碼裡它是 `wWinMain` 的第一個敘述。`build.ps1` 每次建置都跑這項檢查。

### 自測的變異驗證

自測本身也做了變異驗證：撤掉修正後必須打紅，報錯指得出原因，還原後重新建置全綠。

- 第 1 項 5/5（在最終程式碼上重跑）：冷啟動不預熱、不淡化直接換、bypass 瞬切、每次 apply 都重寫 setter、追趕時不吃歷史。
- 第 2 項 4/4：獨佔被分成 INTERNAL、探測改成每秒、仍獨佔卻觸發重新初始化、郵箱不認基準點。
- 追加三件 6/6：就緒不看上游是否停住、就緒顯示成 starting、旁路寫進狀態檔、旁路從狀態檔讀回、WTSAPI32 改回靜態匯入（建置被匯入表檢查擋下）、拿掉 DLL 搜尋限制。
